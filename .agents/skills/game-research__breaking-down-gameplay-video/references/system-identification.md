# System Identification from Passive Gameplay Footage

The task is an inverse problem: the video shows rendered outcomes generated by hidden state, mechanics, player actions, RNG, camera, timing, and capture. One trace often permits several internal explanations. The goal is not to sound certain; it is to construct the most constrained model the footage supports and a footage-faithful reference implementation for everything else.

## Model record procedure

For every hidden question that is not directly stated or visible:

### 1. Define the question precisely

Bad: “How does damage work?”

Good: “For weapon W hitting ordinary enemy class E during upgrade era U, which formula maps the visible base/stat state to displayed per-hit damage, and in what order are the observed modifiers and rounding applied?”

### 2. Freeze direct observations

List only source-backed facts:

- values visible before and after the event;
- target/entity/state;
- PTS intervals;
- repeated observations;
- any explicit on-screen statement;
- source/camera/capture limitations.

### 3. Enumerate candidate models

Include at least:

- the simplest plausible model;
- any model suggested by arithmetic forks;
- target/state/critical/rounding alternatives;
- deterministic versus stochastic candidates where relevant;
- a “display differs from simulation” candidate when UI could be rounded/delayed.

Do not create gratuitous candidates. Add one when it explains the same observations through a materially different hidden rule.

### 4. Derive trace predictions

For each candidate state what else should be visible in the supplied footage:

- a value after another upgrade;
- timing under a different state;
- behavior at another range;
- event order around pause/menu;
- frequency across valid opportunities;
- a cap, discontinuity, or rounding boundary.

Predictions must be falsifiable within the available trace when possible.

### 5. Search for natural experiments

Passive footage often contains accidental controls:

- same action before/after one upgrade;
- same enemy at two ranges;
- same move hit/blocked/whiffed;
- same resource flow before/after one producer;
- repeated cycles under pause or slow motion;
- same track segment across laps;
- same jump with different release/approach;
- same AI state with/without line of sight;
- same attack across multiple targets/statuses.

A natural experiment is useful only when major confounds are named.

### 6. Compare fit and complexity

Record:

- evidence supporting each candidate;
- contradictions;
- free parameters and arbitrary hidden state;
- scope required to make it fit;
- whether it composes consistently with other selected systems;
- residuals or unexplained events.

Do not select a more complicated model because it sounds more game-like.

### 7. Classify identifiability

- `trace_validated`: alternatives make predictions contradicted in the supplied trace; selected model explains all valid cases within uncertainty.
- `supported`: selected model has the best evidence/fit but alternatives are not fully separated.
- `observationally_equivalent`: multiple models reproduce every available relevant observation.
- `contradicted`: model fails valid observations.
- `unidentifiable_from_video`: the hidden property is not encoded in observable output at defensible precision.

This status applies within a declared validity scope, not universally across the game.

## Reference-implementation selection

The baseline clone must still run when the original internals are ambiguous. For `supported`, `observationally_equivalent`, or `unidentifiable` fields, choose an implementation only when required by the clone.

Selection order:

1. preserves every high-support observation and negative constraint;
2. reproduces event order and timing within fixture tolerance;
3. uses the fewest arbitrary hidden variables;
4. is deterministic when randomness is not required by the trace;
5. composes cleanly with other selected systems;
6. is stable outside the narrow exact sample without inventing exotic behavior;
7. exposes uncertain constants as configurable parameters;
8. preserves alternatives in the model record.

Label the choice `reference_implementation`. Never use it to upgrade the historical claim about the original game.

### Example: stacking ambiguity

Visible facts:

- menu states base damage 30;
- upgrade text states “+10 damage” or an ambiguous percentage icon;
- post-upgrade display shows 40 on one target.

Candidates:

- `30 + 10 = 40`;
- `round(30 × 1.333...) = 40`;
- base 30, target vulnerability `×1.333...`;
- critical event;
- internal 39.6 rounded to 40.

Search:

- noncritical-looking repeated hits;
- another target class;
- later damage era after a second modifier;
- pre-upgrade hits on the same target;
- critical marker/color/sound.

If no trace event separates them, select additive `+10` for the clone only if it is the simplest rule consistent with visible text and all later evidence. Preserve every viable alternative.

## Formula reconstruction rules

- Declare input values, output values, units, target/state, and era.
- Enumerate operation order: base → flat → additive percent → multiplicative groups → target modifiers → critical → mitigation → clamp → round → display.
- Test rounding at each plausible stage; UI rounding may differ from simulation.
- Separate caps/floors from saturation caused by UI or target death.
- Do not mix per-hit, per-second, per-target, aggregate, gross, net, or displayed currencies.
- Represent formulas symbolically when numeric parameters are weak.

## State-machine reconstruction rules

- A state requires observable behavioral consequences, not merely a pose.
- Transitions include trigger, guard, effects, priority, interruptibility, clock domain, and persistence through pause/offscreen state.
- Concurrent systems may require orthogonal state machines rather than one giant chain.
- One trace supplies partial transition coverage; absent edges remain absent from the model, not impossible.
- Record unreachable/unseen states separately from known nonexistence.

## RNG and probability rules

From one supplied corpus, distinguish:

- observed trial count and outcomes;
- whether trials are equivalent and independent;
- deterministic schedule candidates;
- state-gated/weighted/without-replacement/pity candidates;
- seed or procedural candidates;
- observed frequency interval, not “true chance.”

For the clone, use a configurable distribution or deterministic sequence that reproduces fixture behavior. Do not claim the original probability without enough equivalent trials.

## Negative evidence rules

No-event evidence is admissible only with:

- an opportunity predicate;
- count of valid opportunities;
- visibility/occlusion checks;
- sufficient state duration;
- no higher-priority state suppressing the event;
- camera and clock validity.

Phrase results as “not observed in N valid opportunities,” not “cannot happen.”

## Cross-model consistency

Before selecting models, check that together they do not imply impossible results:

- chosen cooldown and animation duration overlap correctly;
- spawn schedule produces the observed population under chosen kill/despawn rules;
- economy rates reproduce visible inventory/XP;
- damage, enemy HP, and kill timing reconcile;
- movement and camera models reproduce landmark paths;
- pause semantics agree across timers, AI, projectiles, and UI;
- state priorities explain interrupts and concurrent effects.

Inconsistency reopens the weakest model; do not patch downstream with arbitrary exceptions before questioning the model itself.
