# Test authoring from production code

**North Star:** A reader can compare how four model settings write useful new tests, and whether the testing skill improves those tests, in one standard benchmark table with inspectable native JavaScript.

## Request and scope

The user requested a separate from-scratch benchmark while preserving the existing test-suite improvement benchmark. Use the private backend's Redis-backed work queue: a recent, bounded production capability with real infrastructure. Existing queue tests are private calibration material, never author input. This measures service-boundary integration test authoring, not browser E2E, whole-repository exploration, or general model superiority.

## Contracts

- C-001: Four exact settings, each with Minimal and Skill, one fresh attempt per arm. The source, task, output envelope and runtime are identical; the complete current testing skill is the treatment.
- C-002: Native output is immutable. Two healthy runs and six predeclared source faults test whether suites reject real behavioral faults. No source edits, fake queue implementations, or faults exposed to authors.
- C-003: Two blinded reviewers grade seven craft dimensions from 0 to 1, with line evidence. The user resumed Opus before either review started, allowing one eight-suite batch per reviewer. Opaque domain identifiers receive zero semantic-naming credit; headers, real journeys, independent oracles and unnecessary scaffolding remain explicit criteria.
- C-004: One additive /100 score: fault detection 25, behavioral coverage 20, independent assertions 15, boundary fidelity 10, semantic naming 10, domain structure 5, clarity 5, maintenance economy 5, runnable tests 5. No caps or preservation component. Weights remain frozen. Detection credits source-confirmed failures caused by a fault regardless of error class; diagnosis quality remains a craft criterion. The corrected detection rule was adopted after the round and is disclosed; unresolved infrastructure does not become a numeric failure.
- C-005: Publish Writing new tests with exact raw JS, reviews and method, grouped with suite improvement under one Testing track. Engineering includes all five bucket benchmarks and ranks every model with at least one completed benchmark pair, averaging that model’s available pairs equally. Overall combines available category means using the existing 50/25/25 priorities, normalized over that model’s measured categories. Show all models in the main tables with completed/expected benchmark counts on every row; both conditions use the same paired tasks. Missing results stay unmeasured, never zero-filled. Preserve individual benchmark scores and native evidence. Report all attempts, disagreements and actual usage; no retries or selection for a preferred winner.
